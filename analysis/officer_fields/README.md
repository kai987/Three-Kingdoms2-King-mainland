# 武将 12 字节字段确认

这轮将武将记录与游戏实际显示代码、原 CHR 字形、未修改 ROM 的 Nestopia 截图结合，确认了主要属性、经验、装备及等级编码。不是依据关羽等人物的数值猜属性。

可读模型：`source/recovered/officers.py`；机器可读证据：`fields.json`；完整 237 条已解码记录：`officers-decoded.csv`。ROM SHA256 为 `26c8d921ff5c208191f136480bcd8d7e89c2e4ed40a0ac7b51482bcb52fe2b82`。武将 ID 的初始 record 地址为 `0x022010 + 12*id`，RAM 为 `$63C0 + 12*id`。

|---|---|---|
| +0 | 体：体力 `health` | confirmed：UI 列与数值代码对应 |
| +1 | 武：武力 `martial_strength` | confirmed |
| +2 | 知：知力 `intellect` | confirmed |

| +5 | 状态0时的城市/所在位置 ID `roaming_city_id` | strong inference：有明确城市 ID 读写与搜索排除代码 |

## 属性的直接 UI 证据

bank29 `$B8C9` 的普通武将列表模板（ROM `0x03B8D9`）有 6 列表头。表头实际 64 字节从 `$B909` / ROM `0x03B919` 开始，字形代码在第11、14、17、20、23、26列分别为 `80,84,82,88,86,8A`，对应 CHR 1 KiB page6 的“体、武、知、忠、徳、経”。

bank29 `$BB70..$BB95`（ROM `0x03BB80..0x03BBA5`）逐一读 record 的 `+0..+3`，转换数值并写入相应列；`$BBA4..$BBB0`（ROM `0x03BBB4..0x03BBC2`）读取 `+4`，写入“徳”列。另一个列表模板 `$B809` / ROM `0x03B819` 的表头 `$B849` / ROM `0x03B859` 显示“体、武、知、忠、経、兵”。

![原 ROM 属性表头字形](field-labels-chr06.png)

真实运行截图 `../runtime/game-start.png` 显示刘备“体78、武71、知65、忠--、徳99、経0、レベル1”。它与 ID222 的原始记录对应：`4E 47 41 64 63 00 00 00 BC 02 42 02`。`../runtime/military-selection.png` 的未改 ROM 列表再次显示同一组标题；曹操一行 `82,84,89,--,97,20` 与 ID131 的内部经验1000对应。

这里的原生模拟器截图没有为验证属性而改写游戏数据。下面的变异验证另在 py65 的合成 RAM 中运行实际 ROM 代码，二者明确分开。

## 经验、兵数与位字段

经验显示代码 bank29 `$BBB3..$BBEE` 读取 `+6..7`，乘2，转换 packed BCD 后丢弃最低两位十进制，再显示三位数字。正常 raw 范围0..49999时就是 `floor(raw/50)`；异常 raw≥50000 时高位也因3位宽度被丢弃，例如65535显示310。模型因此按 `(raw//50)%1000` 复现实际显示。

经验增长代码 bank15 `$D7FB..$D8AF`（ROM `0x01F80B..0x01F8BF`）由战斗伤兵累计值奖励经验，并按 `$D85B` 的阈值表 `1000,2000,3500,5000,7500,10000,15000` 更新 `byte11>>4`。每次最多升一个档，保留低4位，同时可能提升武力。完整副作用和实际代码差分验证由 `source/recovered/battle.py` 提供；这里没有重复实现这段增长代码。

等级显示 bank25 `$B5A6` / ROM `0x0335B6` 实际做 `LSR*4; CLC; ADC #1`，证明内部0对应画面等级1。正常等级最高8；无效高档值在这个单个数字显示例程中会截断为个位。

兵数显示 bank29 `$BBF4..$BC12`（ROM `0x03BC04..0x03BC24`）及 bank25 `$B663..$B696`（ROM `0x033673..0x0336A8`）使用 `+8 | ((+9 &3)<<8)`。其他算法可能读写整个 LE16，所以模型同时保留 `troops_raw` 与 `troops_display`，而不丢弃高6位。

原始武将表的兵数 word 最大为1000，仅有 `0,200,300,500,700,800,1000`；初始表没有兵数3500。3500出现于经验 word，共13条。人为设置兵数 raw3500的合成测试证明这个 UI 会显示428。

## 装備文字证明武器与防具

bank25 `$B730/$B770`（ROM `0x033740/0x033780`）读取 byte10。低5位直接选择装备记录0..23；高3位加24选择记录24..31。指针 helper `$B7C1`（ROM `0x0337D1`）读取 bank16 `$9B12` / ROM `0x021B22` 的32个 word，恢复的目标记录范围为 `$9B52..$9D71`。

每个记录17字节：首字节为1 KiB CHR页，剩余16字节为2行×8 tiles。武器与防具使用不同 PPU tile区，但物理字形页由首字节决定。不能用一个固定字体页解码这些文字。

其中可直接阅读短剣、青釭の剣、七星宝剣、関王刀、方天画戟、蛇矛及絹巾、籠手、兜、硬皮、鶴氅、甲冑、聖者の衣、竜鱗の鎧。全部原始 tile 字节、CHR 页、ROM地址、逐条图片及人工转写保存在 `fields.json`。

byte10低5位理论上可取24..31，但它们没有得到正常武器语义验证；模型保留原值并将这种 `weapon_name` 返回 None。通过正常 API 更新武器时仅接受0..23。

## 地形与状态的语义边界

bank25 `$B630` / ROM `0x033640` 从 `byte11>>2 &3` 索引顶部 tile 对，`$B64D` / ROM `0x03365D` 索引底部 tile 对。CHR page6 的原字形可读为：

![地形类别字形](terrain-affinity-glyphs-chr06.png)

0平、1山、2水已经确认，命名为“地形适性”仍保留推断状态。它们不能直接改名为步兵、骑兵、弓兵。值3在初始237记录中未出现，并会越过这个3项字形表，属于未确认范围。

低2位状态的直接代码行为：

- 状态1：bank25 `$AF00..$AF1E` / ROM `0x032F10..0x032F2E` 与剧情记录中的年份和 `$6F00` 比较，等待出现条件。
- 状态2：bank25 `$AF3F..$AF52` / ROM `0x032F4F..0x032F62` 把武将插入城市名册后设置为2。
- 状态0：bank26 `$C099..$C0A7` / ROM `0x0340A9..0x0340B7` 清低2位并将城市 ID `$040E` 写入 +5。bank25 `$BA14..$BA4B` 搜索状态0，同时读取+5并排除当前/邻接城市位置。这支持“在野/未所属位置”解释。
- 状态3：bank25 `$BDC6` / ROM `0x033DD6` 设置3并从城市名册移除；战斗体力归零也有设置3的路径。它表示该上下文的移除/击败/不可用状态；尚不能统一认定为永久死亡。

真实新游戏及军事菜单的 SRAM 与初始表相比仅 ID38、153、222 的记录有变化，低2位分布仍为180条状态1、57条状态2。这个快照没有经历招募、出场、逐将或死亡，不能用它确认所有状态的人类语义。模型保留数值状态码，并显式标出推断名称。

## 执行验证与复现

`validation.json` 的5702个实际 ROM 代码执行案例全部通过，覆盖所有237初始记录的两种列表模式、单字段边界变异、忠100的 `--`、经验和兵数显示、256种装备字段解码、状态转移保留其他位，以及真实武器/防具写入代码的字段隔离。

```sh
python3 scripts/analyze_officer_fields.py '/Users/paulasmith/Downloads/三国志2超级版.nes'
python3 scripts/verify_officer_fields.py '/Users/paulasmith/Downloads/三国志2超级版.nes' \
  --py65-path /tmp/nes-reverse-py65
```

这是字段和局部函数行为的验证，不是完整游戏源代码或实体 FC 硬件验证。`fields.json` 为每项保留 confirmed / strong inference / unresolved 的区别。
