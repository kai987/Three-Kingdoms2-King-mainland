# 单挑玩法规则：独立高层源码

本轮新增[source/recovered/duel_logic.py](../../../source/recovered/duel_logic.py)。它从真实字节行为提取五阶段电脑选招、轮次与持续效果、罵倒/説得、退却追击、投降、临时/永久体力及特殊装备奖励。它不执行指令IR、不调用原ROM代码、没有空渲染函数；数据表由只读ROM提取。旧22主状态控制器及既有证据保留，CPU/图形协议仍由另一个接口处理。

**13,340个实际ROM函数差分样例全部通过。**比较的是声明的游戏字段、完整SRAM和RNG游标；CPU flags、其余寄存器、栈、mapper写入和渲染副作用不在此高层接口契约内。不会把这个结果说成全部NES帧已经由新高层源码独立复现。

## 电脑选招完整规则

`ai_step()`完整实现state2的一个有效子处理器；`choose_ai_action()`连续执行它的真实阶段，最多五次，选中后返回state1/sub3。它无需图形hook，也不执行原代码。所有比较均保留原8位wrap及SBC/BPL行为，R100为原游标0的完整字节拒绝采样。

| 子状态／入口 | 条件与作用 |
|---|---|
| 0 / `$B5D8` | 若当前临时体力≥原模板体力的一半，跳过sub1直接去sub2；否则检查与对手体力、君主身份及`$B7B3`返回值，尝试投降编号3，未选中则sub1 |
| 1 / `$B626` | `u8(当前体力+30)<对手体力`才按`$B7DD`阈值尝试舍身编号6；否则sub2 |
| 2 / `$B659` | 当前体力<30且**按当前体力xor1索引的字节**≥50，才按`$B816`阈值尝试攻击编号2；否则sub3 |
| 3 / `$B689` | 低7位持续计数非零则跳过战术；否则对手知力较低时按`$B851`尝试説得7；其后对手武力≥当前武力时按`$B89B`尝试罵倒8，还检查双方持续状态及当前bit7 |
| 4 / `$B719` | 双方体力按`<31/<61/其他`三档，从72字节表中以RNG&7选择牵制0或攻击2 |

四个阈值中`signed_clip(v)`先取`v&255`，若bit7为1则取0，不能改写为普通整数的`max(v,0)`：

| 入口 | 实际阈值 |
|---|---|
| `$B7DD` | `signed_clip(124 - u8(己临时体力 + max(己武,己知)))` |
| `$B816` | `signed_clip(50 - signed_clip(己武-敌武))` |
| `$B851` | `signed_clip(u8(己知+己徳) - u8(敌忠+己武))` |
| `$B89B` | `signed_clip(max(敌武-敌知,0)+10)` |

部分后置状态检查发生在RNG取样之后，所以即使最后不选招，游标仍可能已经前进。模型没有把这些取样提前省略。

72格fallback表的每个8格单元只含0或2；下表为“牵制格数／攻击格数”，它是原始权重，不把固定种子下的实战频率当成独立均匀随机分布：

| 敌临时体力＼己临时体力 | 0..30 | 31..60 | 61..255 |
|---|---|---|---|
| 0..30 | 3／5 | 5／3 | 6／2 |
| 31..60 | 2／6 | 4／4 | 5／3 |
| 61..255 | 1／7 | 3／5 | 4／4 |

### 两个必须保留的原ROM行为

`$B7B3`把己体力存`$10`后，`$B7BF`的真实字节`4C D7 F2`直接尾跳`F2D7`。它返回**SRAM记录地址高字节**，没有执行随机概率公式。原237条模板体力为30..99，半值最大49；本门槛只有己体力<半值才可到达，而地址高字节至少`$63=99`，因此官方模板域内这条AI投降分支不会选中3。本模型恢复的是所给《超级版》ROM的这个行为，没有凭合理预期修补。

`$B659`加载当前体力并CMP后没有改A。`$B666`的`49 01 A8`是`EOR1/TAY`，所以后续读取`$04B1+(己体力xor1)`，不是读取“对方HP”。当HP为2..29时可访问双方体力缓冲之外的真实RAM。高层API因此使用共享地址空间，而不是仅传两个HP值的理想化公式。

## 轮次与罵倒持续效果

`advance_turn()`保留`$04C0`轮次计数、增后≥3时重采样两方`$04B3/4+R11`比较量和行动方选择，并把计数重新置1。因此正常情况下在首次双方行动后，每两次行动入口重排一次顺序，不能称为每三回合。计数器本身按u8溢出。它根据`$04AB/AC`bit7路由电脑选择或提出玩家肖像/对白请求；返回的请求仍需要宿主实际处理。

罵倒state8 `$C08A`先将施放者`$04B5[side]`设为`$80`。设`S=u8(己知+己徳)`，`D=max(S-敌知,0)`；成功条件为`u8(u8(D+1)+R10)>=110`。R10来自低4位拒绝采样。成功时对方持续值为非零R4再加2，即3..5，同时对方`$04C3=2`；失败不清掉对方原持续值。双方对白编号为`2D/2E`（成功）或`2D/2F`（失败）。然后去state9双边对白。

每次选中行动方时先取其低7位计数；非零就减1并存回，这一分支会清bit7，纯`$80`则保持。正常初始值3..5先减再执行动作，所以对应2..4次低7位仍非零的选中行动机会。bit7已证实会阻止AI再次选择罵倒；玩家分派只检查低7位，不能把这个标记说成所有玩家也永久不能再次使用。

低7位有效时，普通伤害代码将数值roll加20，再将伤害增加`floor(u8(3*伤害)/10)`，总值仍wrap为u8。**更大的roll通常使命中更差，不是纯正向buff。**牵制原本roll<100时进入效果，有持续状态时roll80..99会变为≥100而失败；攻击也更容易超过命中阈值；舍身原本roll<30成功，+20后只剩原roll0..9满足。极端字节值下增加后的伤害bit7可能导致零伤害分支，这也保留。

`strike()`复用已独立恢复的`battle.duel_strike_effect`算术源码，增加真实原attack侧ID匹配、临时HP缓冲、报告伤害字段和子状态推进；没有调用ROM。`commit_confirmed_hp()`等待真实完成信号及A/B确认后才将side0、side1临时HP写入永久记录。同一ID时第二方最后覆盖。它设置`$007E&4`等实际显示完成，未用空渲染替代。`check_strike_result()`随后等显示清位，再继续下轮或写零HP结果2。

## 説得结果表与真实交回路径

`negotiation_choice()`／`persuasion_choice()`恢复全部216格：

1. `u8(己知+己徳)`按`>=180 / >=130 / 其他`分三档，步长72。
2. **敌永久记录体力**按`>=80 / >=50 / 其他`分三档，步长8；不是未写回的临时HP。
3. 敌忠按`>=80 / >=50 / 其他`分三档，步长24。
4. 加`RNG&7`，取原表结果1..4，生成两方对白；结果<3时设置敌`$04C3=2`。

完整数组在[tables.json](tables.json)，216/216格均有原指令执行验证。state9对白后按结果分派：

| 表结果 | 单挑内作用 | 返回路径／后续边界 |
|---:|---|---|
| 1 | 双边对白后回state1继续单挑 | 不写最终战斗结果 |
| 2 | 目标战斗结果1、施放者0 | state15→global5普通攻击场景；不能据battle1本地no-op猜后续地图位移 |
| 3 | 双方战斗结果0 | state14→global3，结束此次单挑 |
| 4 | 等对白及明确A/B确认，目标战斗结果4、施放者0 | state14→global3，战斗结果消费者执行阵营变更／转属 |

这些战斗结果码与武将byte11状态低2位是不同字段。battle bank13 `$C782/$C787`的8项表为`C797,C798,C799,C7DB,C81F,C81F,C81F,C81F`：0/1本地RTS；2在`C799`经验奖励后OR3并清战场槽/cache；3在`C7DB`加入对方俘虏数组并调用忠诚调整；4..7在`C81F/C886`改双方数量/兵数、翻`$0628`阵营位并调用忠诚调整。该下游战斗处理有独立证据，**不是本DuelLogic内新增实现**。

## 退却、投降与零体力

退却是动作1/state4。追击判断`$BB18`取另一方`u8(2*$04B3)`与R100比较；低于阈值跳过体力罚损，否则另一方永久体力扣R10+5（5..14），按实际SBC/BPL裁剪。受击对象与当前actor相反。它直接改武将记录，不先改临时HP，也不改记录status。

非零体力或跳过罚损的退出在`$BC16`轮换actor，写结果1并回state15/global5；零体力分支写结果2并去state14/global3。`BC16`新actor为0时保留入场Y而没有显式清零；`action1_exit_result(incoming_y=...)`保留这一地址行为，正常调用条件Y=0，异常Y也有差分案例。

投降是动作3/state6。七个ruler记录ID匹配者被入口`$D262`禁止选择，退回菜单；其余完成真实投降动画、对白及A/B确认后给actor写战斗结果3，另一方0，去state14/global3。下游将其加入对方俘虏数组。`finish_surrender()`与`finish_action3()`处理的是**动画/对白完成后的游戏写入**，需要宿主显式传完成及按钮输入。

普通扣体归零先产生战斗结果2；单挑本身写HP，不自行OR武将status3。status3与战场移除由后续battle消费者处理，不统一称永久死亡。

## API与等待契约

```python
from source.recovered.duel_logic import DuelLogic, DuelTables

rules = DuelLogic(memory64k, DuelTables.from_rom(read_only_rom_bytes))
result = rules.choose_ai_action()       # valid state2/sub0..4 input
result = rules.attempt_insult()         # exact state8 game effects
result = rules.persuasion_choice()      # exact state7/sub0 game effects
result = rules.finish_surrender(queues_finished=False, buttons=0)
result = rules.commit_confirmed_hp(queues_finished=True, buttons=1)
```

API直接使用共享memory，不自动设定完整场景入口。actor限0/1，数据表长度和ROM哈希固定；其它字节异常按已列契约保留。`choose_ai_action`、`advance_turn`、`strike`等是明确的游戏规则调用，不是NES视频帧。CPU flags与scratch需要另层CPU服务，不得把这些函数直接冒充寄存器hook。

`commit_confirmed_hp`、`finish_surrender`、`finish_action3`必须明确提供`queues_finished`与`buttons`。`negotiation_outcome`／`persuasion_outcome`的sub3也要求两项，缺少即报TypeError且内存不变；无等待的sub1/2可不传。这些函数不会默认文本已经完成。返回的`pending_dialogue_id`、`pending_portrait_id`、`pending_health_display`均表示尚需宿主真正处理的工作。

## 验证和本轮边界

[validation.json](validation.json)中13,340个原ROM差分案例包括：五AI阶段2500例、完整多阶段选择1200例、四门槛公式直接2048例、轮次/全字节持续状态1024例、罵倒2048例、説得816例（全216表格）、退却罚损/门槛/退出1040例、普通攻击及确认/零体写回1992例、説得/投降结束96例、装备奖励576例。全部通过。另有4个**源码接口契约**检查验证缺少宿主信号会报错且无写入，未混入原ROM案例数。

原CPU oracle运行真实函数和所有被调用共享helper，ROM指令没有修改。CPU-only总线的IO假设、构造RAM条件与原完整模拟器的范围不同；本轮未新增“从自然输入达到所有动作”的证明。21段原始函数字节及SHA见[evidence.json](evidence.json)，逐条位置见[logic-ranges.asm](logic-ranges.asm)。1,411个被实际执行的原指令位置包含外部helper，不能当作1,411条高层源码已独立实现的统计。

本轮具体缩减了八组缺口：完整电脑选招；轮次重选与持续衰减；罵倒条件/作用；完整説得权重与结果；退却追击；投降/君主限制；所有特殊装备奖励；确认写回和零体结果的高层整合。剩余边界是显示/音效/动画等待的宿主实现、CPU寄存器协议、完整对白正文、退却结果1回普通攻击后的具体续演，以及自然玩法全分支可达性。原22主状态IR和根整合CPU服务是另一层，不以它们替代本轮高层规则的独立性声明。
