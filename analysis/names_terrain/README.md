# 计略名称、地形与剩余武将字段

这些结论来自原 ROM 的字形、6502 读写代码和原模拟器画面。可读复原模型在 `source/recovered/game_enums.py`；逐字节证据在 `evidence.json`；实际指令执行验证在 `validation.json`。原 ROM SHA256 为 `26c8d921ff5c208191f136480bcd8d7e89c2e4ed40a0ac7b51482bcb52fe2b82`。

名称不是按系列经验推测。bank12 `$ABD9` / ROM `0x018BE9` 从 `$0580[菜单行]` 取得 ID，以 `$AC91` / `0x018CA1` 的 16 项 word 表选名称记录，然后构建两行 VRAM packet。字形页由 `$A8E8` 设置为 `5B 16 02 17` 四个 1 KiB CHR 页。名称记录的 tile bytes、CHR 渲染图片和指针均完整保存在 `evidence.json`。

## 地图 tile 到地形类别的实际读取

bank8 `$B6EF` / `0x0116FF` 按 `x>=16 | ((y>=16)<<1)` 选择 `$A8` 指针所指的四个 chunk ID；在 `$B7CB` / `0x0117DB` 读取 chunk CPU 指针，在 `$B8BB` / `0x0118CB` 读取 mapper 银行值，然后从所选 PRG bank 读取 `((y<<4)&255)|(x&15)` 对应的原 tile。tile≥128 返回类别 0，其余使用 `$B74B` / `0x01175B` 的 128 字节分类表。`$B6E5` 将原类别≥6统一为类别 2，供 AI 使用。

三份 `*-terrain-grid.json` 均保存完整 32×32 的原 tile ID、ROM 偏移、raw class、AI class、镜头坐标及是否为有效图形单元。完整数组包含属性/未使用行，不应把全部 1024 项都称为可行走地图。移动边界检查见 bank8 `$A767..$A789`，限定 x<31、y<20；第15数据行承载属性，物理下半区坐标 y≥16 会先减1。

| raw class | 用于报告的外观标签 | 置信度 |
|---:|---|---|
| 0 | 森林 | strong inference：原模拟器绿色树林像素 |
| 1 | 特殊地形／平滑土色 | 正式名称 unresolved：只确认橙色平面像素 |
| 2 | 平地 | strong inference：原模拟器平地像素 |
| 3 | 水域 | strong inference：原模拟器蓝色水面及水系计略条件 |
| 4 | 山地 | strong inference：山形像素与“山”适性的移动成本 |
| 5 | 城／城砦 | strong inference：敌方主将位置、城墙像素及据点条件 |
| 6、7、8 | 原类别数值 | 具体名称 unresolved；AI 全部映射为2 |

这些外观标签没有被说成官方术语。`native-terrain-patches.csv` 保存 41 个原画面裁切及其坐标、tile、类别、ROM 偏移；没有使用猜测的 metatile 字典作为确认依据。

## “平／山／水”的机械作用与无效编码3

武将 `byte11>>2 &3` 的原字形 0平、1山、2水已在上一阶段确认。本阶段 bank12 `$A7E7` / `0x0187F7` 的实际代码证明它用于地形移动成本：索引为 `terrain_class*4|affinity`。`$063C[单位槽]>=6` 选择第一张表，否则第二张。bank13 `$DB03..$DB45` / ROM `0x01BB13..0x01BB55` 的生产函数已确认：它读取武将低10位兵数、除100，将商缓存到 `$063C[单位槽]`；空武将ID为FF时缓存FF。因此 `selector_byte` 是兵数百位缓存，正常已占用单位的第一表条件就是兵数≥600。它并非兵种或单位所处地形；缓存刷新时机仍由原控制器决定。

下表单元为“第一表／第二表”成本：

| 地形类别 | 平(0) | 山(1) | 水(2) | 无效原编码(3) |
|---:|---:|---:|---:|---:|
| 0 | 3／2 | 5／3 | 5／3 | 0／0 |
| 1 | 4／3 | 4／3 | 4／3 | 0／0 |
| 2 | 2／1 | 3／2 | 3／2 | 0／0 |
| 3 | 5／3 | 6／5 | 3／2 | 0／0 |
| 4 | 5／3 | 3／2 | 6／4 | 0／0 |
| 5 | 6／4 | 6／4 | 6／4 | 0／0 |
| 6 | 6／4 | 6／4 | 6／4 | 0／0 |

验证范围是原表的 7 行（0..6）与 4 列，不把越过表尾的其他类别作为合法成本。返回 X=成本、A=行动点减成本的8位结果，Carry 表示行动点足够。两张表的 ROM 位置为 `0x018833` 和 `0x01884F`。

编码3在初始237武将中未出现。它的第四列全部0，合成 oracle 中 2,043 个编码3成本案例确实得到0；这并不证明存在合法“免费移动适性”。bank25 `$B630` 的顶部字形表只有 `62 63 64 65 60 61` 三项。编码3会越过表尾读取下一函数的 `A0 0B`（LDY #$0B 指令字节）；64个编码3字形案例验证了这个越界读。它没有得到第四种正式名字。

## 剩余状态与兵数高6位

`byte5` 的赋值含义仍为 strong inference 的在野/未入名册位置：bank26 `$C099` 清状态低2位并写当前城市 `$040E`；bank25 `$BA14` 搜索状态0武将时读取这个位置并排除当前/邻接城市。正常所属关系由城市名册表示，不能把 byte5 当成永久势力所有者。

低2位是已确认的编码，但人类名称保持各自置信度：

| 值 | 已观察代码行为 | 名称范围 |
|---:|---|---|
| 0 | 清所属状态，写 byte5 城市位置 | strong inference：未入名册／在野 |
| 1 | 检查剧情年份再进入名册 | strong inference：等待出场 |
| 2 | 插入城市名册后设置2 | confirmed transition：在名册 |
| 3 | 体力归零或城市删除路径 OR03 | confirmed removal flag：移除／击败；永久性依路径 |

状态3具体写入路径包括 bank12 `$B5D8` 的体力归零处理、bank25 `$BDC6` / `0x033DD6` 的城市名册删除。后者保留 byte11 高6位，删除名册项并紧缩名册。单挑 bank24 `$D060` 只把临时体力写到武将 byte0；bank23 `$B9C8` 的 `$0515/$0517=2` 是**战斗结果码**，不是武将状态2。单挑结尾交回 battle 状态11后还有独立的结果分支，不能把所有结果2或状态3统一命名永久死亡。

战后主状态13/子状态1还有明确的清零路径：bank13 `$CDC8..$CDD6` 对选中非领袖记录执行 `AND #$FC` 清低2位，然后把当前城市 `$050E` 写入 byte5；领袖另走 `$CDE3..$CDEC` 的 `ORA #$03`。`$D101..$D166` 的选择列表来自战场槽和俘虏数组，未直接按武将低2位筛选。其上游是否已把击败武将的单位ID清为FF，会影响谁进入列表。因此清零操作的存在不能单独证明状态3可以复活。完整 Nestopia 的注入单挑场景也观察到体力归零时低2位维持原值；该证据明确属于合成 fixture，详见 `analysis/duel_fsm/runtime/injected-core/validation.json`。

`byte9` 的上6位仍无已确认的独立语义，但消费者和清零行为已经定位：

- UI bank29 `$BBF4` 与减兵 bank12 `$B68B` 都先 `AND #3`，有效兵数为低10位。
- `$B6B5..$B6BE` 将剩余值写回 byte8/9，所以即使减兵数量为0，byte9 上6位也会清零。
- AI 排序 bank8 `$AEC6..$AEEE` 比较未掩码的 byte9/8；计略11条件 `$ADDD..$ADE8` 将任何非零 byte9 作为兵数条件。这些代码会观察高6位，却没有证明它们是6个独立状态标志。
- 初始237条记录的上6位全部0。复原 API 同时保留原 LE16 和 UI/战斗低10位视图。

合成 `raw troops=$0400` 的 UI/主要战斗视图为0，但计略11的 AI 兵数条件为真；数量为0的减兵写回会将它变为 `$0000`。这个边界明确说明为什么不能在所有算法中提前丢弃原高6位。
