# 普通攻击场景控制源码复原

可执行模型：`source/recovered/attack_state_machine.py`。这是从原机器码提升的复原源码，不是原始开发源码。`program.json` 保存 5,170 条提升指令；`state-catalog.json` 保存全主／子状态入口、条件、内存写入、外部调用和13张有边界证明的内联指针表；`handlers.asm` 提供对应 bank／CPU／ROM地址。原 ROM 没有被修改。

## 战场、普通攻击与单挑的转移

普通攻击由 NMI模式 `$0078=4` 驱动，原renderer fixture 中全局 `$007A=6`。主状态5/子状态1 `$CD59` 等待淡出标志 `$0087` 的bit7，然后调用 `$E768`。`$CD61` 之后把攻击子状态加1、全局状态设为7、单挑 `$04A8/$04A9/$04AA` 清0，并将双方ID及控制码写入 `$04AD/$04AE` 和 `$04AB/$04AC`。

参与控制码3在单挑输入中变为 `$80`；当第一控制码非0且第二码为0或1时，两个参与者的位置交换。原代码在 `$CD85` 和 `$CDAA` 各有一套写入路径。可读函数 `handoff_to_duel(memory)` 已完整复现这些条件和写入；它不修改武将体力或 `byte11` 状态。

主状态5/子状态2 `$CDCF` 回读两名武将的真实体力到 `$05AC/$05B7`，恢复攻击主状态0/子状态1，再检查 `$0514/$0515` 与 `$0516/$0517` 的结果。当结果码为1时，`$CE10` 为相应一方写 `$0550` 或 `$0554=1`。结果码的人类语义需要与具体结果分支分开，不能直接当武将低2位状态。

返回战场的明确出口是主状态4/子状态2（子状态6为同入口别名）`$A3F2`：淡出bit7有效时，写 `$0500=11`、`$0501=0`、`$007A=3`。可读函数 `return_to_battle(memory)` 已逐值验证所有256个淡出字节。

## 可执行IR与明确外部依赖

`AttackStateMachine(memory,hooks)` 的 `step()`、`phase(main,sub)`、`run_entry(entry,stop_pc=...)` 执行提升后的控制／ALU／内存逻辑，不从 ROM 取指。所有同bankpair直接调用都递归提升，6502 Carry、借位、寄存器、临时指针和栈行为被保留。`$EADE` 通过已独立验证的 `ControlHelpers` 实现；`$EE07` 保留真正的5字节内联目标及恢复约定。

bankpair之外的24种依赖在 catalog 的 `hooks` 中逐调用位置列出，包括图形绘制、输入、消息、场景切换及固定bank算术。它们通过显式 hooks 实现，缺失时抛出依赖错误。验证 adapter 执行这些 helper 的原机器码，因此当前验证能证明控制源码的等价性，却不代表这24种外部 helper 都已独立恢复为高层源码。每例结果保留了实际外部调用列表。

- 174个入口案例：58合法主／子状态组合×按钮0／1／2，逐例比较CPU寄存器、flags、栈、全部2KiB RAM、8KiB SRAM、mapper银行及VRAM。
