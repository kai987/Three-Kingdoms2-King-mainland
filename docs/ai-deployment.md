# 原作AIの初期配置：武将順と四つの機械的グループ

今回の対象は、戦闘開始時の原作AIが使う武将順・人数配分・座標候補である。主将を保った武力比較、勢力スロット別の人数表、グループ別の座標読み出しを接続する。戦闘中の戦術AI全体を置き換える改修ではなく、グループIDに未確認の「突撃」「側翼」「防御」などの名称を付けない。プレイヤーとAIには同じ可視矩形・占有・山水の合法性を適用する。

本書は原指令と本作への適応を分けて記録する。原CPU観測の925例は完了しているが、今回追加する実装の全体回帰・最終ブラウザー結果は別に集計する。ローカルの変更であり、push・リモートCI・オンライン公開を意味しない。

## 固定ROMと呼び出し順

対象ROMのSHA256は`26c8d921ff5c208191f136480bcd8d7e89c2e4ed40a0ac7b51482bcb52fe2b82`。以下のAI本体はphysical8。Archiveの`source/recovered/battle_setup_ai.py`は原指令からの復元コードで、原作者のソースではない。ROM・Archive・OpenEmu・利用者の保存状態は変更していない。

| 処理 | 原番地／確認できる読み書き |
| --- | --- |
| 初期化と人間／AIの選別 | `B130–B1AF`。`0507`の下位nibbleが守備側、上位が攻撃側の勢力スロット。`B4C2`のレコードポインターでbyte3がちょうど3ならAI処理へ進む |
| 守備AI、次に攻撃AI | `B159/B181`。`6F91`を0／10、主将strategyを0にし、`B371→B1B0`を呼ぶ。人間側はここで並べ替えない |
| 非主将の比較と交換 | `B371–B3D1`、交換`B3D2–B3FC`。人物recordのbyte1を比較し、`0664/0628/063C`を同時交換 |
| 人数表とグループ割当 | `B1B0–B257`。勢力スロット、側、非主将人数から2byteを選び、四nibbleをstrategy1〜4の人数として使う |
| 来向ごとの座標表 | 守備`B2AE–B30D`、攻撃`B312–B36C`。`050E`の目標都市と`052A`の出発都市を原隣接表で照合する |
| 実際の座標書込 | `B266–B2AD`。主将は先頭の2byte、非主将はグループ別游標から`packed_y,x`を読む。1人配置するごとにそのグループ游標だけ2進める |

起戦の固定ルーチン`E1B4`はselector40でphysical8/9を選び、`E1B7 JSR A003`から`B130`へ入る。これは人間の`C204/C218`・逐将編集より前である。既存場面への復帰用`0500==11`の別分岐はselector44の`A006`へ入り、同じ初期化を再実行しない。Archiveの`scene_initialization.py:51–55`と、実際の`B130`入口で保存された戻り先`E1BA`が一致する。

主な作業域は`6F91`の側先頭0／10、`6F94`の非主将人数、`6F99..6FA0`の両側四人数、`6FA1..6FB4`の20槽strategyである。番地をまたいで用途が変わる`0020/0021`は、初めは人数表のポインター／作業値、formation呼出後は座標表のポインターになる。フレーム末の値だけから途中の入力を推定しない。

## 主将固定と同武力の交換

`B371`はその側の10槽の非`FF`人物数を数え、1を引いた非主将人数を`6F94`に置く。通常の、主将から連続して有効人物が入り後ろが`FF`の名簿を前提とする。空の軍勢や穴だらけの名簿のbyte回り込みを、通常の配置仕様として移植しない。

主将の槽0／10を除き、非主将数を`n`とすると、全ての隣接比較を`n−1`回繰り返す。次の武将の武力が現在以上なら交換する。従って単なる安定降順ではなく、同値も交換される。例えば非主将9人が全て同武力なら、原順`[1,2,3,4,5,6,7,8,9]`は`[9,1,2,3,4,5,6,7,8]`になる。主将を含む全員を一括ソートしたり、同値を人物IDで決め直したりしない。

交換するのは人物ID、同じ槽の軍種／側マーカー、百人隊の対応配列であり、人物recordの武力自体は変更しない。原作は座標未設定の段階でこれを実行する。本作はこの比較順を**人物IDから配置候補への割当**に使い、戦局の両軍リスト自体は並べ替えない。既存の名簿・主将・保存・奇門の固定順序契約を保つための適応であり、原20槽を復元したとは扱わない。読み込みでも位置や行動順を並べ替えない。

## 勢力スロットと六つの人数表

原`B4D3`の7本のポインターは`6F07,6F0F,…,6F37`。各レコードbyte0が**現在の君主人物ID**、byte3が操作主体である。原`B1B0`は現在の人物IDを読まず、`0507`から渡された固定の勢力スロット番号を使う。

physical26の原君主通知表`C3BB`と`C93A`は、どちらも人物ID`[173,8,131,138,222,220,182]`。既存の[ROM名字形の照合表](../game/config/portrait-identity-map.json)と実際の`B130`入口のレコードで、次の対応を確認できる。

| 原勢力slot | 初期君主／原人物ID | 人数表family |
| --- | --- | --- |
| 0 | 董卓173 | 0 |
| 1 | 袁紹8 | 1 |
| 2 | 曹操131 | 2 |
| 3 | 孫策138 | 0 |
| 4 | 劉備222 | 2 |
| 5 | 劉璋220 | 1 |
| 6 | 馬騰182 | 0 |

戦後のAI継承`C25D→C260 F368→C263`は、対象勢力の同じレコードのbyte0だけに後継者を書く。プレイヤーの`BF8A–BFA1`、内政の`CB52–CB64`も同じスロットへ新人物を書く。勢力slotを現君主IDへ置き換える処理ではないので、継承しても人数表familyは変わらない。

人数表はphysical8の`B3FD..B468`、108byte。守備側3family、攻撃側3familyで各18byteを持つ。非主将人数`n=1..9`の参照位置は次のとおり。

```text
address = B3FD + side_offset + family_offset + 2 × (n − 1)
side_offset   = 守備0／攻撃54
family_offset = family0:0／family1:18／family2:36
counts        = [byte0上位, byte0下位, byte1上位, byte1下位]
```

四人数の合計は`n`。武将比較後の順にstrategy1、2、3、4を人数分ずつ割り当て、主将は0のままにする。非主将0人では人数表を読まず主将だけ置く。この表は人物の性格や歴史的な戦術評ではなく、原ROMの機械的な分岐である。

本作は安定した勢力IDを対応させ、`wei/shu→family2`、`yuan_shao/liu_zhang→family1`、`wu/dong_zhuo/ma_teng→family0`とする。`sun_jian`を呉、`liu_yan`を劉璋系として扱うのは、本作の年代別勢力への**明示的な系譜別名**であり、原7slotにその人物専用の表があったとは主張しない。他の追加勢力はfamily0の共通fallbackを使う。現任君主の名前や能力・推測した性格でfamilyを切り替えない。

## 四グループの座標と共通の安全条件

守備`B2AE`は目標の原隣接から守備区画を選び、原点表の先頭へ`32×区画索引`を加える。攻撃`B312`は同じ隣接の攻撃区画を使い、`34×区画索引`を加える。索引は都市別の配対番号で、東西南北コードではない。115都市の対応と、原隣接がない場合の方向推定は[既存の地域適応](directional-deployment.md)を維持する。

座標は`packed_y,x`の順で読む。主将は両側ともbyte offset0／1。非主将strategy1〜4の最初のbyte offsetは、守備`B30E=[2,8,12,20]`、攻撃`B36D=[2,12,22,28]`。その後はグループごとに2ずつ進む。元の点表を単純に先頭から人数分取る配置ではない。

原AIのこの経路は`C447`の矩形判定も、`D6B6`の占有判定も呼ばず、軍種・地形から合法性を再検査しない。人間の自由配置と原AIの座標読み出しが同じ検査だったとは記載しない。今回の768個の原隣接×側×familyの10将配置、計7680点の観測では、**矩形外13回、既出座標との重複9回**があった。これは各配置ベクトルの槽ごとの発生回数で、異常な元レコードを去重した13件／9件ではない。この768例には可視範囲外の点はなかった。以前の[原点表全体の異常一覧](../game/config/references/original-battle-deployment-v1.json)とも集計の母数が異なる。

本作は利用者指定の共通ルールに従い、プレイヤーとAIとも原半開矩形∩可視31×19、`packed_y15`の除外、重複／占有の排除を使う。山・水は追加禁止しない。候補の不採用理由は`outside_grid→outside_zone→occupied`の順で一つを記録し、その区画の安全な元既定表から最初の空き点を選ぶ。安全な点が尽きれば拒否し、座標のclampや新しい点の創作はしない。AI同士は守備、次に攻撃の順で占有を引き継ぐ。プレイヤー参加戦はAI全員を先に置き、将来の人間側武将は占有に含めない。

原候補とその異常値は出典から削除せず、`intended`に元の`x,packed_y`、`repairs`に人物IDと理由を残す。修正後だけの図を原点表と見せず、原AIに存在しない安全検査を原作そのものと呼ばない。

## 実装・保存の境界

原人数表・グループ游標・固定slot対応は[新しい参照JSON](../game/config/references/original-battle-ai-deployment-v1.json)と[参照の抽出・検査](../tools/battle-deployment-original/ai_reference.py)で管理し、ROMを必要とする抽出と、出荷済み参照だけの検査を分ける。実行時に研究Archiveや抽出スクリプトをimportしない。[純粋planner](../source/remake/battle_ai_deployment.py)は`binding/profile/order/groups/positions/intended/repairs`の新しい値を返し、入力の戦局・名簿・乱数を変更しない。

新しい行軍到着で始まる戦局だけに[取引サービス](../source/remake/battle_auto_deployment.py)からこの計画を使い、プレイヤーの[逐将配置](manual-deployment.md)と接続する。AIの初期入力を任意の`extended.auto_deployment`に次の閉じた形式で保存する。

```text
{schema: "tk2-auto-deployment-v1",
 sides: {AI側: {binding: {family, policy, original_slot},
                 roster: [{id: 正規文字列ID, martial: 整数0..255}, ...]}}}
```

プレイヤー参加戦はAIの片側、AI同士は両側を保存する。`binding.policy`は`original_faction/lineage_alias/expanded_default`、元slotがない追加勢力の`original_slot`は`null`。正式座標は既存の`tactical.positions`を使い、計算できるgroupsやpositionsを新記録へ重複保存しない。表示では保存した初期入力から`binding/profile/order/groups/intended/repairs`を純粋に導出するだけで、新たな配置やAI行動を実行しない。

人間側の準備中はAIの初期名簿と座標が計画どおりか厳格に検査する。完了後は初期の勢力・人物集合と元の転属台帳を確認し、移動・損傷・籠絡後の現在位置を初期計画に縛らない。旧戦局へ新しい人数表や記録を後付けしない。`auto_deployment`のない旧pendingは従来の固定既定点を維持し、読み込み時にAIを新方式で置き直す用途には使わない。非公開の既成戦場fixtureも、新しい到着処理を通らない限りこの初期化へ入らない。

並べ替え・分組・座標計画は乱数を抽選せず、機動力・日数・命令書・追加兵糧を消費しない。守備プレイヤーの最後の確定後に攻撃AIが通常行動する既存順序は保つ。戦闘中の戦術決定、虚兵・連環・奇門、既定の行軍・補給は今回の初期配置を根拠に変更しない。

## 繁體中文摘要

本輪接原AI起戰部署：主將不動，非主將按武相鄰比較，後者大於或等於前者就交換，完整比較重複`n−1`輪；同武不是穩定排序。依固定勢力slot、攻守與非主將數，從原108byte表取四組人數，機械ID1–4按組別游標讀原陣區座標；不猜「側翼」等戰術名。原slot0–6依次董卓、袁紹、曹操、孫策、劉備、劉璋、馬騰；繼任只換同record的君主人物ID，不改slot或profile。魏／蜀用family2、袁紹／劉璋用1、吳／董卓／馬騰用0；孫堅與劉焉是明示的本作系譜別名，其餘新勢力用family0，不按現任君主性格猜配。

原AI直接取點，並沒有玩家的矩形／占位檢查。768組10將原CPU向量共出現矩形外13次、重複9次，均按實際槽位發生次數計，不能當作去重原表異常數。本作維持玩家／AI相同的原矩形、可見格、去重占位與山水合法性，安全修正另標適配、不刪原證據。925例分成3個既有真caller捕獲重放與922個受控CPU例；本輪本機2834項Python／Rust、65CJS、27組來源核查、29劇本雙後端與4個桌面／觸控瀏覽器驗收皆通過；詳見上表。只對新到達戰局建立`auto_deployment`，舊戰局不補策略、不重排、不重跑AI，亦未推送或發布線上。
