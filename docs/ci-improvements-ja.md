# 表示変更のCIとブラウザ検証時間

単挑の外観設定、既存の第一・第二版の原画／プロンプト、素材の生成ツールと対応テストは、戦闘表示・人物表示として明示的に分類します。PNGの再構築、SHA、余白、原画保護、実際の装備との対応、全劇本の基本整合性は残します。原画・プロンプトと説明だけを変更した場合は公開しません。未知の兵器、世代、パス、共有ルールやCI自身の変更は、引き続き全体検証になります。

ブラウザはデスクトップ・タッチ各2分割、各runnerの`workers:1`を維持します。既存の並列実行に加え、[レビュー済みの実測値](../tools/browser-tests/case-durations.json)を用いて、長いケースから予想合計時間の短い組へ配ります。新しいケースは明示的な120秒の仮の重みで必ず含め、所要時間未計測のIDを表示します。

```sh
node tools/browser-tests/verify-shards.mjs desktop-chromium
node tools/browser-tests/verify-shards.mjs touch-chromium
node tools/browser-tests/run-shard.mjs touch-chromium 1 --list
```

`verify-shards.mjs`は固定版Playwrightの実際の`--list`を使い、各組の内容と全ケースの和集合が一致すること、重複・欠落がないことを確認します。`run-shard.mjs`は同じ計画を実行します。これにPlaywrightの`--shard`を重ねてはいけません。選択範囲が1ケースだけなら、もう一方は明示的な0ケースとなり、実行件数を水増ししません。

CIは各ケース・端末・試行の時間をJSONとして保存し、最後のゲートで4報告のcommitと完全性を検証します。`browser-timing-summary-SHA`には次を保存します。

- `summary.json`：実行したケース、試行、各組の見積りと実測合計。
- `summary.md`：読みやすい時間表。
- `suggested-case-durations.json`：次回の時間基準の更新候補。

更新候補は自動適用しません。新しい原画の変更でテストの範囲が縮むことと、測定値によってその範囲の実行順・組み合わせが変わることは、別々に検証します。時間表はケースの累計時間であり、環境構築・アーティファクト取得・アップロードを含むrunner全体の時間ではありません。

通常CIとは別の定期全体検証と、共通ルール変更時の全体検証は維持します。詳細は[検証手順](testing.md)と[Playwrightの分割仕様](https://playwright.dev/docs/test-sharding)を参照してください。

地図の表示用画像は地図グループで検証し、正式ビルドと地形素材の再生成確認も行います。画像のSHAだけが変わる場合は、対象が登録済みで旧版・新版のSHAが実体と一致することを確認します。経路計算用の画像、水系、都市座標、未登録ファイルの変更は全体検証を行います。

公開対象の`main`へのpushでは、同じリポジトリでマージ済みのPRについて、成功した実行回の検証記録を確認します。PRが検証した仮マージの親コミット、ソースツリー、必要なテスト範囲が一致すれば、PRで済んだ検証を再利用します。`main`のコミットで改めてWebをビルドし、WASMの動作とCPU参照との一致、公開ファイルのSHAと内容を確認してから、その成果物をPagesに渡します。記録がない場合、期限切れや照合不能の場合は全体検証を行います。定期・手動の全体検証は従来どおりです。

[PR #18](https://github.com/kai987/Three-Kingdoms2-King-mainland/pull/18)の全体検証は33分56秒でした。マージ後の[main](https://github.com/kai987/Three-Kingdoms2-King-mainland/actions/runs/42800226142)では同じソースツリーの検証を再利用し、正式ビルドと公開ゲートを含め2分44秒で完了しました。別の作業ツリーで実際の検証記録のツリー・試行番号・対象範囲をそれぞれ不一致にすると、全体検証に戻り、再利用だけの結果は公開ゲートで拒否されました。

Python・Rustの戦役テストは引き続き各6組です。[前回のmain](https://github.com/kai987/Three-Kingdoms2-King-mainland/actions/runs/42785966219)と[PR #18のCI](https://github.com/kai987/Three-Kingdoms2-King-mainland/actions/runs/42795317222)のunittestログから求めたモジュール時間を後端別に平均し、長いものから合計の短い組へ割り当てます。未計測のモジュールには60秒を割り当て、登録済みファイルが各後端で1回ずつ実行されることを確認します。次回の計測用に、各組のモジュール別時間をCI成果物へ保存します。

新しい6分割をローカルで実行し、Python・Rustのそれぞれで147モジュール、1,559テストがすべて成功しました。

同じ静的成果物を使ったローカルのChromiumでは、分割前は両端末とも約2分42秒、分割後は長い組がデスクトップ86.3秒、タッチ86.1秒でした。全体実行では2組を別々のrunnerへ割り当てます。PR #18の実測値をその配分に当てはめると、ブラウザ最長組はデスクトップ30分02秒から27分33秒、タッチ30分53秒から28分48秒になります。再配分の比較ではWorkerをもう1回起動するための6秒を見込み、ローカルで観測した総実行時間の短縮は加算していません。

AIバランス観測ツール`tools/campaign-balance/run.py`とその固定の単体テストだけを変えた場合も、全戦役の長時間回帰にはしません。通常CIでは小さい制御fixtureを使う短いhelperテストを残し、長時間の観測は専用の定期／手動ワークフローに分離します。観測ツール専用の変更ではゲームを公開せず、未登録の別ツールや共有ルールの変更は全体検証を維持します。

途中保存の`run.py`・`replay_saved.py`・`parallel_saved.py`も個別の登録対象です。工具だけの変更は原生参照・217年の保存互換性・短いhelper回帰を保ち、長い実戦の再実行や公開を自動選択しません。未登録の同名類似工具、混在するゲーム変更、分類器自身の変更は従来どおり判定し、必要なら完全検証へ戻します。
